1 · Separate checking from choosing

Our question today is fixed: “How long does standard shipping take?” We introduce check_evidence between retrieval and routing. It returns two state updates: evidence_ok, a Boolean (True or False), and reason, a short explanation.

START → retrieve → check_evidence
                     ├─ evidence_ok is True  → generate → END
                     └─ evidence_ok is False → fallback → END

The check node records a decision. The router reads that decision and returns a node name. This uses the same node/state and conditional-edge behavior described in the official state guide and conditional edges guide.

def choose_next(state: State) -> Literal["generate", "fallback"]:
    return "generate" if state["evidence_ok"] else "fallback"

builder.add_edge("retrieve", "check_evidence")
builder.add_conditional_edges("check_evidence", choose_next)

The conditional edge now leaves check_evidence, so the decision is stored before the router reads it.

2 · A small, visible checking rule

For this exercise, the check rejects empty evidence and accepts a passage containing the exact phrase standard shipping takes, ignoring letter case. Everything else is rejected. Read check_evidence in the Python example.

This rule is deliberately narrow.

It works for today’s controlled passages and fixed question. It does not understand meaning: “Standard shipping arrives in 3 to 5 business days” is useful evidence but fails the phrase check. A misleading sentence containing the accepted phrase could pass. We are learning where to put a check and how its result travels, rather than building a general relevance checker.

3 · Follow the state in Case A

  1. Before retrieval: state contains the shipping question and case: "a".
  2. After retrieval: state also contains a returns passage about 21 days and its source.
  3. After checking: those fields remain. State now also contains evidence_ok: False and reason: "The passage does not state standard shipping duration.".
  4. At routing: the router reads False and selects fallback.
  5. After fallback: state contains an answer explaining that the retrieved evidence cannot answer the question. Generate did not run.

Retrieval still selected the wrong passage. The new check prevents this example from quoting it as an answer; it does not repair retrieval or find a better passage.

5 · Challenge the rule

Check after your edit

The passage still answers the question, but evidence_ok becomes False and fallback runs: the phrase “standard shipping takes” is absent. This is a checking error, not a retrieval error. Compare the question, retrieved passage, and check output to locate it.

Now change the condition to accept either "standard shipping takes" or "standard shipping arrives" in the lowercased passage. Rerun B and also A and C to check that the rejected cases still take fallback.

One possible code change
passage = state["passage"].lower()
if "standard shipping takes" in passage or "standard shipping arrives" in passage:
    return {"evidence_ok": True, "reason": "The passage states standard shipping duration."}

Replace the old phrase condition and its return with these lines inside check_evidence, after the empty-passage check. B should now reach generate. A and C should still reach fallback. This improves the rule for these examples; other wording can still fail it.
