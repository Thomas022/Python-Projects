1 · Define success before running

Your assistant should release a supported answer and stop when it cannot produce one. A case therefore needs both an input and an expected outcome. An evaluator compares actual behavior with that expectation. Primary reading: offline evaluation.

ModeExpected outcome
goodreleased
repairreleased

check_answer checks a draft inside the graph. Our new evaluator checks the graph’s final outcome outside it. These are different decisions: a rejected draft can lead to a passing evaluation when rejection was expected.

2 · Run the baseline

The Python example reuses Lesson 17’s graph and runs each case with fresh state. Keep both Python files in lessons/. Retrieval and generation remain simulated.

The script loads your saved project .env automatically. When tracing is enabled, these runs send toy questions, evidence, drafts, and results to your workspace; look for lesson-18-baseline-good and the other mode names. 5 · Know what this check proves

This evaluator checks only the outcome label on four toy cases. It does not independently verify the answer text, broad document coverage, or real model behavior. A bug could return a wrong answer with the expected label and pass. Later checks can compare answer content and evidence too. Official guide: code evaluators.
