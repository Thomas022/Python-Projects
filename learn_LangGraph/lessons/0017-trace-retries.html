1 · Summary versus trace

Lesson 16’s summary tells us repair rejected one draft and eventually released an answer. The trace lets us inspect which draft failed and what information reached the retry. The Python example keeps the same graph and gives each run a name such as lesson-17-repair.

This graph uses simulated retrieval and generation. There is no model call or model-provider key to configure. LangSmith records the graph execution when tracing is enabled. See the official LangGraph tracing guide.

2 · Enable tracing in your saved settings

Use the LangSmith account from Lesson 03. If needed, follow its account setup or the official key setup guide. Open the project’s .env file and check these settings. Reuse the key saved in Lesson 03; enter it only if the key field is still empty.

LANGSMITH_API_KEY=your-key-here
LANGSMITH_TRACING=true
LANGSMITH_PROJECT=document-qa-lessons

Lesson scripts automatically load .env each run. Existing terminal exports take precedence; use a fresh terminal if you previously exported settings. Match LANGSMITH_ENDPOINT to your account’s deployment if it is outside the default US region. Set LANGSMITH_WORKSPACE_ID if your key requires workspace selection. Official tracing configuration.

Tracing sends this exercise’s question, evidence, drafts, feedback, and results to your LangSmith workspace.

Open LangSmith, select the workspace and tracing project configured above, and find lesson-17-good, lesson-17-repair, and lesson-17-stuck. If your workspace groups runs under agents, use the corresponding agent/environment. Open each trace’s Details view and expand its run tree. Look at graph-node runs; you may also see routing/helper runs, which are not additional generation attempts.

A successful terminal run proves local execution. Confirm the named trace appears separately. If it does not, check the terminal for upload errors, the saved .env settings, and your workspace, project, and region. You can practice the same comparisons in the local node log while resolving setup, but label those observations as local rather than live traces.

4 · Follow repair across three boundaries

  1. First generate output: draft says $50 and generation_attempts is 1.
  2. First check_answer input: draft says $50 while passage still says $5. Its output sets answer_ok to False and supplies repair_feedback.
  3. Second generate input: repair_feedback contains the required evidence and citation; passage still says $5. generation_attempts is still 1 on input because the node increments it while generating.
  4. Second generate output: draft says $5 and generation_attempts becomes 2.
  5. Second check_answer output: answer_ok is True and repair_feedback is cleared.
  6. Release and summarize: answer says $5; run_summary.outcome is released.
Find the same feedback twice

Compare the first check_answer output with the second generate input. The feedback should match. That shows the correction reached the retry; the retry’s output shows whether the correction was followed.

In stuck, feedback also reaches the second generate call, but the simulated generator ignores it. A trace proves what was passed between nodes; it does not guarantee a correct answer.
